### Vertical feel — measured proposal (no edit until Felipe/the Architect decide)

**What is known:** both axes share one deadzone (1.4 dps), one gain (18 px/deg), one low-pass (α 0.28), the same 8 ms BLE accumulation and ±60 clamp; the only vertical-specific settings are axis 0 and sign +1. The bench capture shows the vertical channel carrying ~70 % of the horizontal channel's angular rate while the unused Z axis carried as much as the horizontal one (numbers in Discrepancies). Two candidate causes: **H-a** mount geometry on the LEFT temple tilts the pitch axis so a nod projects partly onto `gz` (the vertical channel sees an attenuated projection); **H-b** physiology — people nod slower and shorter than they turn, so a symmetric gain under-serves the vertical axis. They need different fixes, so I measure first.

**Measure (no code, Felipe's hands, one ≤ 90 s recording):** motion-monitor mode, start the guided IMU probe and enter `CAPTURE_FREE_RUN` with the second Button A tap during `PREPARE_STILL`; over the TCP capture the firmware streams `IMU,ms,usec,stage,gx,gy,gz,…` rows. Felipe performs, with a marker before each: 10 s **yaw only** (slow left-right turns, ~±30°), 10 s **pitch only** (slow nods), 10 s **roll only** (ear toward shoulder), 10 s still. Scratchpad analysis: per segment, RMS per axis → a 3×3 energy matrix, and the per-segment peak rate. Decision rule: if ≥ 90 % of the pitch-segment energy is on `gx` → **H-b**; if a material share (> 20 %) is on `gz` → **H-a** (and the matrix gives the tilt angle θ = atan2(RMS_z, RMS_x) of the pitch segment).

**Decide (Felipe / Architect):**
- H-a, pitch mostly on one axis → change `kVerticalGyroAxis` (and sign) to that axis — config only.
- H-a, split → add a mount-tilt rotation to `MotionConfig` (`vertical = cosθ·g[vert] + sinθ·g[aux]`, with `aux_axis` and `tilt_deg` fields, defaults 0 = today's behaviour) — `motion_controller.{h,cpp}`, `config.h`, wiring in `main.cpp:177-188`.
- H-b → add `vertical_pixels_per_degree` to `MotionConfig` (default = horizontal gain, so existing tests and Wokwi are unchanged), set it from the measured ratio `18 × RMS_yaw/RMS_pitch` (the uncontrolled bench ratio 1.37–1.44 predicts ≈ 24–26 px/deg); deadzone stays 1.4 dps unless the still segment shows a different vertical noise floor (it is a noise parameter, not a feel parameter); α unchanged.
- Rejected as a vertical-only fix: macOS tracking speed / acceleration (global, both axes).

**Verify:** new native cases in `test/test_motion_controller` (per-axis gain/rotation math, default-equivalence with today's config, sign), Wokwi `pointer_direction_and_accumulation` stays green (+1 check if a field is added), all gates + `CHECK_IMAGE,PASS`; this is portable code, not board-level init, so the lane is the normal OTA (Felipe's go) → A/B bench with the same task (move between two vertically and two horizontally separated targets; count corrections) → **Felipe's feel verdict is the `[REAL]`**; if it is not better, the change is reverted on the branch, not tuned in the run.

## Concerns

- [HIGH] `upload_ota.sh` does not stop on a failed `pio run` (no `pipefail` under `/bin/sh`, see Discrepancies), so the `check_image.py` gate protects the build but not the OTA lane; a failed build followed by the uploader would push the previous `firmware.bin`. Proposed fix (one file, `sticks3/scripts/upload_ota.sh`, outside every fence, not board-level init): run the build without a pipeline and test its status — `if ! "$pio_bin" run -e "$pio_env" > "$build_log" 2>&1; then cat "$build_log"; echo "Refusing OTA: build failed" >&2; exit 1; fi; cat "$build_log"` — and additionally require `grep -q '^CHECK_IMAGE,PASS' "$build_log"` and that `firmware.bin` is newer than the script's start (`find "$firmware" -newer "$build_log"`). Verified by a dry run with a deliberately failing ceiling (`DRAM_CEILING` via the existing `env.Value`) on a build-only invocation — no device contact — then the normal gates. **Not applied without the author's/Felipe's go (Question 8).** Operational mitigation until then, for every OTA in this plan: build first in its own command, confirm `[SUCCESS]` and `CHECK_IMAGE,PASS` in that output, and check the `firmware.bin` mtime before calling the uploader.
- [HIGH] The device could not be reached from this host (mDNS did not resolve). Step 0's TCP identity check is a hard gate: if the greeting is not `ff1f7d2` / slot app1 / `img=VALID`, the bench does not start and the state is reported first.
- [MEDIUM] Cable **detach** detection rests on TinyUSB suspend/unmount events, not on VBUS sensing; a lock that arrives late (or only on the next host poll) would be a real finding for the Architect. The ≤ 3 s bound in B1.3 is my proposal for "bounded"; it is not a threshold to relax inside the run.
- [MEDIUM] B2 needs a second BLE central; without one the item is recorded "not exercised" (T16 keeps it `[PENDING]`), not inferred from the whitelist code.
- [MEDIUM] During B4 the pointer is armed for 10 minutes; the only on-device click channel is closed and the camera click must be OFF, so the worst case is cursor motion — but the Mac should show an empty desktop so nothing gets dragged.
- [MEDIUM] The vertical proposal's per-axis gain / rotation is a `MotionConfig` extension; it is portable code and keeps today's behaviour by default, but it is still a firmware change that gets its own OTA and Felipe's verdict — it is not bundled with the acceptance items.
- [LOW] Battery: the bench drained ~1.1 %/min while streaming + BLE + Wi-Fi + display; B4 alone costs ≈ 11 %. Start the soak ≥ 40 %.
- [LOW] The rollback canary stays deferred; at merge time the deadline/attempt-budget rollback paths remain `[TEST]`-only and T17 says so already.
- [LOW] `EVENT,MOUSE_OUTPUT,LOCKED` is silent when already locked; my pass criteria only expect it on armed→locked transitions, so no false fails from that.
